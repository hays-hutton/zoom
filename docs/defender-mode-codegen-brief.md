# Defender-Mode Codegen: A Brief for Frontier Model Providers

> A proposal for providers (Anthropic, OpenAI, et al.) to supply *defender-mode*
> code generation against intent-specs (e.g. Commons Format), turning the
> generator into the upstream point of leverage in software supply-chain defense.

## The ask, up front

Offer a **defender-mode generation capability**: given an intent-spec (prose
intent + machine-checkable eval suite), generate an implementation that is

- **(a) conformant** to the contract,
- **(b) deliberately divergent** from other valid implementations, and
- **(c)** accompanied by a **fault-divergence score** that measures how
  differently it *fails*, not just how differently it reads.

## Why a provider — specifically — should care

1. It's a safety differentiator you can actually ship and certify against, not a
   policy statement.
2. The coordination problem that defeats every other defense ("you can't
   coordinate the commons") **doesn't apply to you** — there are ~5 of you, and
   the standard only needs the *protocol* coordinated, not the internals.
3. The asset under attack is generated by you. You are already the most upstream
   point of leverage in the software supply chain. This makes that position
   defensive instead of a liability.

## The logic flow

### Stage A — The equilibrium that held for 25 years is broken.

- **P1:** "Given enough eyeballs, all bugs are shallow" worked because attacker
  and defender attention were in rough parity, and volunteer attention was free.
- **P2:** Frontier exploit-finding scales with compute and shows *no observed
  plateau* — it ramps and layers. (This is the load-bearing empirical premise.
  It is currently the *observed* behavior; the burden is on the skeptic to show
  a ceiling, and none has appeared.)
- **C1:** Tokens replaced eyeballs, but tokens are *priced and asymmetric* where
  eyeballs were free and distributed. The parity is gone. Visibility becomes a
  liability.

### Stage B — The real failure is an externality, not "shared bytes."

- **P3:** In OSS, *defense* is a public good funded by unmotivated volunteers,
  while *value-at-risk* accrues privately to thousands of deployers. The
  defender's personal stake ≈ 0; the global VaR ≈ enormous.
- **P4:** A no-plateau attacker amortizes: pay cost `c` once, capture the entire
  summed global VaR.
- **C2:** The vulnerability isn't that the code is shared — it's that **defense
  is socialized while value is privatized.** That gap is what AI now exploits at
  scale.

### Stage C — The repair: re-internalize defense by distributing intent, not bytes.

- **P5:** Ship the spec + evals; each consumer generates their own *private*
  implementation.
- **P6:** This does two things at once: (a) it **deletes the attacker's
  summation** — no single break captures the global base; and (b) it
  **re-privatizes defense** — the deployer now owns the implementation *and* the
  VaR, so they spend on defense proportional to their actual stake.
- **C3:** The motivated party (who holds the value) is finally the one funding
  the defense. The externality is closed.

### Stage D — But the repair has a hole: divergence must be *manufactured*, not assumed.

- **P7:** Same spec + overlapping training data → implementations *cluster*.
  Naive generation gives a small effective N and correlated faults. Divergence
  you hoped for is not divergence you have.
- **P8:** The dangerous bug class (contract/logic flaws — missing validation,
  auth ordering) is invariant under any semantics-preserving change, so
  divergence can *only* ever protect the implementation layer (idiom, language,
  memory). That's still the majority of the amortizable attack surface — but
  only if the divergence is real.
- **C4:** Fragmentation is sound in principle and hollow in practice **unless
  someone guarantees the divergence.**

### Stage E — The provider is the only actor who can guarantee it.

- **P9:** Divergence injected at generation time — varied algorithms, data
  structures, control flow, and target language, semantics-preserved and
  eval-verified — is *engineered*, not accidental.
- **P10:** Critically, **the divergence is a property of the target, not a
  secret.** The attacker has frontier models too — but the locks are structural
  to each deployed instance. Knowing every door has a different lock doesn't give
  you the key. So this is robust to the attacker being as capable as the
  defender; it is *not* security-through-obscurity.
- **C5:** A provider that supplies measured defender-mode divergence converts
  fragmentation from a slogan into an enforced property. This is the missing
  manufacturing step.

## The three bounds (state these honestly — they make the ask credible)

1. **Semantic ceiling.** Injected randomness must pass the evals, so it's
   semantics-preserving by construction — it cannot diversify contract-level
   logic bugs. Those are defended by the *compounding shared eval suite* (every
   exploit found anywhere becomes a permanent eval case everywhere), not by
   divergence. Divergence and evals are complementary, not substitutes.
2. **Generator-root monoculture.** If divergence is at the leaf but one model
   generates the world's code, the *model* is the new billion-endpoint target —
   poison it once, corrupt every leaf. → The requirement is **independent
   multi-provider** participation: coordinate the *protocol*, keep the
   *internals* independent. This is why the ask goes to "all," not one.
3. **Measurement.** "Non-trivial randomness" is an assertion until it's scored.
   The deliverable that fixes this is a **fault-divergence metric**
   (mutation/fault-injection: do two implementations *fail* differently?). That
   single instrument is simultaneously the diversity certificate *and* the
   independence registry the ecosystem currently lacks.

## The complete program (where defender-mode codegen sits)

| Threat layer | Defense | Who supplies it |
|---|---|---|
| Implementation bugs (idiom, language, memory) | **Engineered divergence** | **Providers ← the ask** |
| Contract/logic bugs (shared by all impls) | Compounding shared eval suite | Spec authors + ecosystem |
| High-VaR head (crypto, parsers, serialization) | Formal artifacts + VaR-reduction | Specialized, few modules |
| Generator-root monoculture | Independent multi-provider participation | All providers |
| Enforcement / adoption | Lockfile as insurance/compliance artifact | Insurers, regulators |

## What we're asking you to build

1. A **defender-mode generation flag/endpoint** for spec-driven codegen with a
   divergence objective alongside the correctness objective.
2. A **fault-divergence score** emitted with each generation (the certifiable
   "non-trivial" definition).
3. A commitment to **protocol coordination, internals independence** — agree the
   spec/eval/scoring standard with peers; share nothing about how your generator
   achieves divergence.

## The one-line version

> Frontier exploit-finding broke OSS because it lets attackers amortize one break
> across a globally-shared, volunteer-defended codebase. Distributing *intent*
> instead of *bytes* deletes the amortization and re-internalizes defense to the
> party that holds the value — but only if the divergence between implementations
> is real. Providers are the one actor positioned to manufacture and certify that
> divergence, and the coordination only requires the handful of you to agree on a
> protocol, not on internals.

## Timing

The prevailing prior is still "visibility is fine, shared code is good." The
trigger that flips it will be the first *publicly attributed* no-plateau
mass-exploitation event — after which "visibility is a liability" stops being a
contrarian take and becomes the insurance underwriter's checklist. This brief is
deliberately written to be persuasive *before* that event, which is the harder
and more useful case.
